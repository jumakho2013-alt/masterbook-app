# База данных

Всё, что относится к Supabase: схема, права, функции, крон-джобы и edge-функции.

```
supabase/
  migrations/   — схема БД. Единственный источник правды.
  functions/    — Deno edge-функции (публичная запись, админ-подтверждение платежей)
```

## Главное правило

**Схему меняют только миграцией из этой папки.** Не через SQL Editor в дашборде,
не «быстро поправлю руками». Если изменение сделано мимо репозитория — его нет
ни в код-ревью, ни в истории, ни у того, кто поднимет проект с нуля.

Так уже было: до сентября 2026 в репозитории лежал один снимок `supabase-schema.sql`
от 18 июня с 6 таблицами, пока в облаке жили 10 таблиц и 25 миграций. Поднять
рабочее окружение по репозиторию было физически невозможно.

## Как добавить миграцию

Имя: `<YYYYMMDDHHMMSS>_<что_делает>.sql` — метка времени в UTC, дальше короткое
описание латиницей через подчёркивания. Порядок применения = порядок имён.

```bash
npx supabase migration new my_change     # создаст файл с правильной меткой
# ... пишешь SQL ...
npx supabase db push                     # применит на связанный проект
```

Требования к содержимому:

- **Идемпотентность.** `if not exists`, `create or replace`, `drop policy if exists`
  перед `create policy`. Миграция должна переживать повторный запуск.
- **Комментарий «почему», а не «что».** Что делает — видно из SQL. Ценно то,
  какую проблему это закрывает и что сломается, если откатить. Смотри
  `*_fix_profiles_upsert_needs_update_on_id.sql` как образец.
- **Ничего разрушительного без нужды.** `drop table`, `drop column`, снятие
  `not null` — только осознанно и с пометкой в комментарии, что будет с данными.

## Ловушки, которые уже стреляли

**Колоночные гранты против `upsert`.** `supabase-js .upsert()` PostgREST
разворачивает в `insert ... on conflict (id) do update set <все колонки тела>` —
включая `id`, `user_id`, `created_at`. Если колоночный `grant update` их не
покрывает, запрос падает с `permission denied for table ...`, а обычный `PATCH`
при этом проходит. Пуш в облако обрывается на первой же таблице и синхронизация
ложится молча — тесты этого не видят, потому что supabase в них замокан.

Меняешь гранты — сверься со списком колонок, который реально отправляют
`clientToRow` / `serviceToRow` / `appointmentToRow` / `financeToRow`
в [`src/lib/cloudSync.ts`](../src/lib/cloudSync.ts), и запусти приложение:
`permission denied` видно в логе Metro сразу.

**`HTTP 204` не значит «получилось».** PostgREST отвечает 204 и когда RLS
отфильтровала все строки. Проверять результат записи надо запросом к БД,
а не кодом ответа.

**Права на таблицу и RLS — разные вещи.** RLS ограничивает *строки*, гранты —
*колонки*. Политика `auth.uid() = id` не мешает мастеру выставить себе
`premium = true`, если на колонку выдан `UPDATE`.

## Проверка состояния

Список применённых миграций на сервере лежит в `supabase_migrations.schema_migrations`.
Сверить с репозиторием:

```bash
ls supabase/migrations | sed 's/\.sql$//'
```

Оба списка должны совпадать. Расхождение = кто-то менял схему мимо репозитория.

## Edge-функции

- `functions/book` — публичная онлайн-запись с сайта. Вызывает RPC
  `book_appointment` (атомарная проверка слота под advisory-локом).
- `functions/admin-payments` — подтверждение пополнений. Проверяет e-mail
  вызывающего по списку `ADMIN_EMAILS`, затем зовёт `confirm_payment` под
  `service_role`. Клиенту `confirm_payment` недоступна намеренно.

Деплой: `npx supabase functions deploy <имя>`.
